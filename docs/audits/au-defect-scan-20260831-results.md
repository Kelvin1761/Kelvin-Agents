## D 節 —— WinningTime regex（已修）

```python
# 舊：硬要 M:SS.mmm
RE_WINNING_TIME = re.compile(r"Winning Time\s+(?P<time>\d{1,2}:\d{2}\.\d{3})")
```
但跑少過一分鐘嘅賽事寫 `Winning Time 58.420`。60 個 cache 頁面 2,603 個
`Winning Time`：捉到 1,868、**漏走 735 = 28.2%**，而漏走嘅每一個都係 <60 秒
（54.810 … 59.770）—— **唔係隨機丟失，係所有短途賽**。

修完 **71.5% → 99.0%**，其餘七個欄位全部 ≥98.8%。第七次同一失敗模式
（前六次：`Settled`、`L600 Delta`、試閘 header、finish 名次、`margin` 的 `L`、
賽果封頂）。

**連帶效果**：`EXP-20260831-07` 嘅 WinningTime 速度指數重測本來喺 38.6% 覆蓋
（偏向長途）上做，得出「dev/holdout 唔一致＝噪音」。補好覆蓋到 **87.9%** 之後
判決變**明確 REJECT**（holdout 每個 k 都負，k=2.0 CI [−0.0144, −0.0003]、
k=5.0 [−0.0220, −0.0004] 全負）。

## G 節 —— 兩個 overlay 唔喺發佈閘（已補）

`data_contract` 讀 `python_auto.feature_scores`，但 `wet_form_feature` /
`proven_class_feature` 係 `python_auto` 嘅 **sibling**。所以濕地 overlay 個
prior 校錯（0.5 vs 實測 0.3758）、中位數 −1.49 咁多個月，而九個 suite 全綠、
發佈閘全綠 —— **冇任何閘門睇到**。

實作要留意兩樣（測試已鎖）：
1. **Overlay 中性點係 0.0 唔係 60** → 加 `neutral_point()`
2. **有適用性條件**：乾地全場 0.0 係**正確行為**。冇呢個條件，每個好地場次
   都會令 `wet_form_feature` 嘅 `neutral_rate` 變 100%，發佈閘會攔死所有乾地
   場次。所以只喺 soft/heavy 場次觀察。

基準已重新 calibrate：20 個欄位，濕地 overlay 中性率 16.76%、場內散開度 1.339。

## A 節 —— 騎練 prior 漂移咗但唔使改

| 常數 | code 值 | 校準窗（08-05 前） | 現行窗（08-05 起） |
|---|---:|---:|---:|
| `_JOCKEY_WIN_PRIOR` | 0.1271 | **0.1267** | **0.1115** |
| `_PLACE_RATE_PRIOR["trainer"]` | 0.3673 | **0.3676** | **0.3238** |

校準當時**完全正確**；08-05（Racenet 剷走、騎練數據轉 Sportsbet 個人頁）之後
輸入分佈整體下移 −12%。**唔係語料組成**（08-05 起城市 0.1117 vs 鄉道 0.1108，
幾乎一樣）。

但重校**冇量到排名效果**（乾淨窗 980 場：−0.0001 [−0.0023, +0.0023]）。
原因同濕地 overlay 唔同：收縮 k=20 而 rides 通常 100+，所以**有數據嘅人幾乎
同幅平移，場內互相抵銷**；只有冇數據嘅（騎師 2.0%／練馬師 8.5%）唔動，太細
量唔到。濕地嗰個之所以有效，係因為罰則**隨經驗遞增**，唔會抵銷。

⚠️ 記低呢個分辨方法：**prior 校錯有冇後果，睇佢造成嘅偏移係「常數」定
「隨樣本量變化」。** 常數偏移喺場內排名度自動抵銷。

   之下得出「唔一致」，補好之後得出「顯著負」。
