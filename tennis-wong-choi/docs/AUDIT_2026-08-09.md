# Tennis Wong Choi — Technical Audit

**Date:** 2026-08-09 · **Codebase:** 147 Python files, ~22,300 LOC · **Tests:** 212 passing

Every number below was measured against the live `tennis_wc.db` during this audit. Where a
claim is an inference rather than a measurement, it says so.

---

## 1. Current architecture and end-to-end workflow

The production path is narrow. `scripts/tennis_daily_schedule.py` (launchd, twice daily)
shells into `tennis_wc.cli` and uses **4 of the 44 registered subcommands**:

```
network-check → review-date (settle yesterday) → run-daily (price + report today)
              → weekly-review (Sundays) → archive
```

`run-daily` expands to:

```
ingest_odds (Sportsbet scrape)      market_odds_snapshots
        ↓
ingest_matches / entity_mapping     matches, players, tournaments
        ↓
feature_builder                     feature_snapshots  (JSON blob per player per match)
        ↓
probability_model                   predictions.model_probability   ← match winner
        ↓
props/daily.price_ace_props_for_date
   ├── ace_model        (ladder, player aces, match aces)
   ├── player_model     (games, handicaps, win-a-set, first-set, exact-set-score, counts)
   ├── games_model      (hold-based expected total games)
   └── set_distribution (BO3 outcome distribution)
        ↓
props/registry.VALUE_PROFILES       is this a value selection?
props/calibration                   learned model-vs-market blend weight
        ↓
prop_tracker                        the evidence base
        ↓
props/settlement + strategy         scorecard, ROI, the gate
        ↓
reports/daily_report                the card
```

Result ingestion runs on a separate branch: `betting/ledger._refresh_results_for_date` →
ESPN (composite) + TennisMyLife + TennisExplorer → `match_results.score_json` → `settle_props`.

**Structural observation.** `reports/daily_report.py` is **5,041 lines — 23% of the entire
codebase** — and `betting/ledger.py` is 2,351. Together, two files that are nominally
"reporting" and "bookkeeping" hold **33% of all code**, and both contain real decision logic
(`_recommended_picks`, `_prop_source_quality`, the result resolver). This is the single
biggest obstacle to understanding the system.

## 3. Current player-prop logic — and the opportunity matrix

This is the most decision-relevant table in the audit. "Coverage" = share of the 1,988
matches that have any market where Sportsbet offers this one. "Settleable" = share of stored
results carrying the statistic needed to grade it. "Takeout" = median overround.

| Family | Market coverage | Settleable | Takeout | Walk-forward ROI (n) |
|---|---|---|---|---|
| **game handicap** | **38.2%** | **99.8%** | **5.3%** | −3.1% (604) |
| first set winner | 29.3% | ~100% | 7.7% | +12.3% (70) |
| win at least one set | 22.4% | 100% | 7.8% | −6.6% (195) |
| player total games | 20.5% | 99.8% | 7.2% | −17.2% (159) |
| match total games | 20.5% | 99.8% | 7.2% | not staked |
| set betting (exact score) | 58.0% | 100% | **10.0%** | +119% (3) — noise |
| set handicap | 7.8% | 100% | — | +32% (13) |
| **player aces** | **6.3%** | **26.0%** | 7.2% | **+18.7% (44)** |
| match total aces | 6.5% | 26.0% | 7.2% | −12.3% (45) |
| **player double faults** | **0.0%** | 26.0% | — | **we model a market that does not exist** |

**The strategic tension, stated plainly.** `player_aces` is the only family that passes the
evidence gate — but it is offered on **6.3% of matches** and only **26% of results carry ace
counts** (ITF does not collect serve statistics at all). Its addressable universe is roughly
125 matches over three months. Even a perfect ace model cannot carry the system.

`game_handicap` has 6× the market coverage, near-total settleability, and **the lowest takeout
on the board (5.3%, i.e. ~2.7pp per side)**. It is currently the biggest loser, but for
reasons this audit identifies as fixable inputs rather than an unfixable market.

## 5–10. Findings

Each finding is classified **Critical / High / Medium / Low** and by type:
*(DI)* data integrity · *(M)* modelling · *(B)* betting strategy · *(A)* architecture ·
*(O)* operational/reporting.

### CRITICAL

**C1 — Elo and rank are read from mutable single columns with no as-of date.** *(DI + M, look-ahead)*
`features/feature_builder.py:124,130` reads `players.overall_elo` and `players.current_rank`.
`modelling/elo_builder.py:114` overwrites `players.overall_elo` with the rating computed over
**all** history each time it runs. There is **no Elo history table**. Any feature snapshot built
or rebuilt after a match therefore embeds a rating that already contains that match's result —
and **3,776 of 16,046 snapshots (23.5%) were built after match day**, along with 368 predictions.
The same repository already contains the correct pattern: `features/opponent_rank_buckets.py`
filters `match_date < as_of_date` and uses the opponent's ranking *at match date*. Two
definitions of the same concept, one right and one wrong.
*Fix:* an `elo_history(player_id, as_of_date, rating)` table; features read as-of.
*Test:* assert no feature snapshot's provenance timestamp postdates its match date.

**C2 — 864 duplicate player identities fragment the history that the prop models depend on.** *(DI)*
`players` holds 5,954 rows; **864 normalised names appear more than once** (many 3×), and
**1,026 of those duplicate-name rows appear in actual matches**. For 160 names the match history
is split across more than one id, stranding **3,057 history rows** on non-primary duplicates.
Since `ace_model` requires `_MIN_HISTORY = 10` prior matches, a player split 70/8/0 across three
ids can be silently rejected as "too thin to model" while the data exists.
This is also the most likely driver of "41.9% of priced players have no history at all".
*Fix:* canonical `player_identity` table with alias mapping; merge on ingest, not at read time.

**C3 — The match-winner model does not run for 73% of what we price, and 7 of 9 prop families
consume its output.** *(M)*
`overall_elo` is missing from **72.9%** of feature snapshots. By tier: tour 75.9% covered,
Challenger 59.1%, **ITF 1.2%**, **UTR 0.8%** — and ITF is ~85% of the Sportsbet board. With no
Elo backbone and no active nudge, `_combine_components` returns `sigmoid(0) = 0.5000` exactly:
**24.3% of all 5,035 predictions are exactly 0.5000, and 80% sit within ±0.05 of it** (model SD
0.0867 vs market 0.2292). Correlation with actual game margin: **model r = 0.226, market r = 0.453**.
*Partially addressed 2026-08-09:* `_match_prob_map` now drops exact-0.5 rows so they cannot be
priced. The underlying coverage gap remains.
**The encouraging half:** restricted to matches where Elo *is* present (n=456), model Brier
0.2461 vs market 0.2438 and AUC 0.6117 vs 0.6281 — **level with the market**. The method is not
broken; it is starved.

### HIGH

**H1 — Odds snapshots contain in-running and post-match prices.** *(DI, leakage)* — **fixed today**
The scraper re-reads matches while they are played: match 113 holds 48 snapshots of one selection
between 10:20 and 13:54, one set-betting selection ranges **1.26 → 41.0**, and 2,919 snapshots
(2.5%) were fetched after match day. `_two_way_odds` resolved duplicates with "later id wins".
Impact on the prop evidence was small (−4.00% → −3.54%), because the large swings sit in
`set_betting`, which we have staked three times. Impact on ad-hoc research was total: a
cross-market experiment during this audit produced **+58% ROI with bootstrap P(ROI≤0)=0.000**,
entirely from in-running prices.
*Fixed:* `price_ace_props_for_date(..., earliest_odds=True)`, set by the replay.
*Test needed:* fail loudly if a backtest reads more than one snapshot per selection.

**H2 — `reports/daily_report.py` (5,041 lines) holds betting decision logic.** *(A)*
`_recommended_picks`, `_prop_source_quality`, `_closest_blocked_legs` and the leg construction
for all nine families live in the reporting layer. Selection quality for ace families is
computed one way here and another way in `settlement.prop_roi_report`. A reporting module
should not be able to change which bets exist.

**H3 — Tour labelling is unreliable.** *(DI)*
**270 matches** have two players whose `players.tour` disagree; **771 matches** have a `tour`
that disagrees with player A's. `matches.tour` is `UNKNOWN` for 1,365 of 3,987. `_aces_gradeable`
gates ace value bets on `tour == "ATP"`, so mislabelling silently suppresses or admits bets.

**H4 — Surface resolves for only 47.7% of matches.** *(DI + M)*
1,903 of 3,987. Surface is a first-order ace and games feature; `count_profile` and
`player_ace_profile` fall back to all-surface when thin, which is sensible, but half the board
never gets the surface split at all.

**H5 — The prop families are priced by one generic spine.** *(M)*
Seven families derive from a single scalar — `P(A wins)` — pushed through closed-form
transforms. There is no per-prop feature set. The ace model is the exception (built from ace
history) and is the only family that passes the gate. Kelvin's instinct here is correct and the
evidence supports it.

### MEDIUM

**M1 — `player_double_faults` models a market Sportsbet never offers.** *(A)* 0.0% coverage,
0 scorecard outcomes, yet it holds a family slot, a pricing path, a `ValueProfile` and gate state.

**M2 — 725 placeholder matches (18.2% of `matches`).** *(DI)* Both sides are the same player id —
`TBD` (1634) or `Unknown Player` (1646). They carry no odds, predictions or results, so they are
inert, but they distort every count and any future join. *Real duplicate fixtures: zero* — match
identity is otherwise clean.

**M3 — Two market-blend systems coexist.** *(A + M)* The legacy `temper` + fixed `_MARKET_SHRINK`
(0.35 in `player_model`, **0.25 in `ace_model`** — same concept, two values) and the learned
`calibration.blend_with_market`. Duplicated across 7 call sites as `if model_weight is None:`.
Production now uses the learned path everywhere (fixed today); the legacy branch survives only
for tests.

**M4 — Three backtesters, all untested, one orphaned.** *(A)* `backtester`, `external_backtest`,
`combiner_backtest`. Only `scripts/replay_prop_strategy.py` is leakage-safe and current.

**M5 — 13 LLM agents outside the production path.** *(A)* Reachable only via `run-agents`.
Not harmful; pure carrying cost and a source of confusion about what actually decides a bet.

**M6 — Retirement handling is inconsistent.** *(DI)* `retired` is present on 884 results (26.9%)
but flagged true on 47. 15 results carry a winner and no games. Whether a retirement voids or
grades a games prop is decided in `settlement`, not declared once.

### LOW

**L1 — 19 providers, several are stubs** (`betfair` 7 lines, `statsperform` 7, `odds_api` 19).
**L2 — 44 CLI subcommands, 4 used daily.**
**L3 — Coincidental shared constants** (`0.65` means both a shrink and a quality floor).

## 15. Recommended target architecture

```
ingest/          scrapers, one per source, each with a parser test
identity/        canonical player + tournament ids, alias tables   ← NEW, fixes C2
warehouse/       matches, results, per-match statistics, odds snapshots (with as-of)
history/         as-of feature store: elo_history, rank_history     ← NEW, fixes C1
props/
  models/        one module per prop: aces.py, games.py, sets.py    ← fixes H5
  pricing.py     model distribution → fair probability
  value.py       fair vs market → edge, EV, confidence              ← single source of truth
  gate.py        family evidence → may this bet                     (already good)
  staking.py
evidence/        prop_tracker, settlement, scorecard, ROI           (already good)
replay/          walk-forward harness                               (already good)
report/          rendering ONLY — no decisions
```

Rules: one definition per metric; nothing in `report/` may change what is bet; every model
declares its required features and **fails loudly** rather than defaulting.

## 16. Which prop to rebuild first

**Recommendation: `game_handicap` — with `player_aces` kept running as the control.**

| | player_aces | game_handicap |
|---|---|---|
| Market coverage | 6.3% | **38.2%** |
| Settleable | 26.0% | **99.8%** |
| Takeout | 7.2% | **5.3%** |
| Current ROI | **+18.7%** (n=44) | −3.1% (n=604) |
| Why it is where it is | works, tiny universe | fed by a broken input |

Aces is the only family with a positive record, and it should keep running — but 6.3% coverage
and 26% settleability cap it permanently. Game handicap is where the volume, the settleability
and the cheapest prices are, and its failure is diagnosed, not mysterious: it is priced off a
match probability that is a coin flip 80% of the time (C3), through a share curve borrowed from
a different quantity that cannot express a margin beyond ±3.1 games when 72.1% of matches finish
outside that band (fixed today).

**Prerequisite:** C3. Game handicap cannot be rebuilt before the match probability is real, and
the match probability cannot be real until ITF Elo exists (C2 + the TennisExplorer feed built
today make that possible for the first time).

### What the measurement said

After the corpus finished (220 days, 87,720 matches, 12,228 new players) and
Elo was rebuilt over it, **as-of Elo now resolves for both players on 1,621 of
1,988 priced fixtures — 81.5%, up from 37.7%**, and 16,647 players carry a
rating against 3,033 before. The scored population with Elo present moved from
615 fixtures to 1,017.

| on 1,017 fixtures with as-of Elo | Brier | AUC |
|---|---|---|
| stored model (Elo + 9 logit nudges) | 0.2413 | 0.6717 |
| market | **0.2200** | **0.7018** |
| raw Elo, no nudges | 0.2389 | 0.6280 |

Read carefully, because the two rows say different things:

* **The nudges help ranking and hurt calibration.** Against raw Elo they gain
  0.044 AUC and lose 0.0024 Brier. Deleting them, which the first measurement
  on 615 fixtures suggested, would throw away real ordering information. The
  fix is to calibrate the combined output, not to strip the signals.
* **Neither beats the market.** 0.2413 and 0.2389 against 0.2200; 0.6717 and
  0.6280 against 0.7018.

**One caveat that matters.** The `model` row comes from predictions stored
under the OLD regime -- built from the mutable rating, before the corpus
existed and before as-of lookups. It is not what the model would say today
with 81.5% coverage. Rebuilding feature snapshots and predictions over the new
ratings is the first step of Phase 5, and until that runs the honest current
comparison is raw Elo against the market: **0.2389 vs 0.2200 Brier, 0.628 vs
0.702 AUC.** We are behind, on a fair measurement, for the first time.

### Phase 5 so far

**Rebuilding predictions over the new ratings changed the model, not just the
coverage.** Prediction spread went from SD 0.0867 to **0.1472**, and the share
sitting at exactly 0.5000 from 24.3% to **0.2%**.

| on 1,017 fixtures with as-of Elo | Brier | AUC |
|---|---|---|
| model, rebuilt | **0.2273** | 0.6711 |
| model + Platt calibration | 0.2283 | 0.6680 |
| market | 0.2200 | 0.7018 |
| raw Elo | 0.2389 | 0.6280 |

Two earlier readings reverse, and both reversals matter:

* **The nudges earn their place after all.** Rebuilt, the full model beats raw
  Elo on both Brier (0.2273 vs 0.2389) and AUC (0.671 vs 0.628). The earlier
  "the nudges are harmful" reading was an artifact of feeding them a broken
  Elo. Measuring a component before fixing its input tells you about the input.
* **The calibration I built does not help** (0.2283 against 0.2273). It is
  measured and not shipped.

The gap to the market narrowed from 0.0213 to **0.0073** Brier. Still behind.

**The game-margin slope.** Refitted against the rebuilt probability on 1,241
settled matches: bucket means now run −2.78 → +3.61 monotonically with r=0.320,
against r=0.221 and non-monotone before. The fit is **11.26 games per unit of
probability**; the market's own probability fits 11.17 on the same outcomes, so
it is a property of tennis. The borrowed share curve implied 6.15.

**A regression I introduced, found and fixed.** Every one of the 3,622 rebuilt
snapshots scored `data_quality` 0, against 53.9% at 65+ for the older ones.
Derived props lose their value flag below 65, so the replay fell from 1,133
settled bets to 108 and `player_game_handicap` produced zero. The cause was
`validate_data_freshness` comparing odds timestamps to `datetime.now()`:
rebuilding a May snapshot in August makes both odds datapoints "stale", each an
error, and four errors floor the score. **The data had not changed; only the
clock had** — the same defect class as the first version of the look-ahead
check. An isolation run confirmed it: with the margin slope reverted but the
predictions rebuilt, the replay returns the identical 108 bets and +3.93%.
That +3.93% is not a result; it is the tenth of the board that survived.

A second instance of the same shape sat behind it. Feature snapshots accumulate
rather than upsert -- 4,353 (match, player) pairs hold more than one, 18,447
extra rows, going back to 2026-05-09 -- and the pricer gated on
`MIN(data_quality_score)` across the whole match, so it read the worst score
ever recorded rather than the current one. No rebuild could improve the gate
however much better the data became. Reading the latest snapshot per player
moved matches clearing the gate from 248 of 2,391 (10.4%) to **1,988 (83.1%)**.
The odds table had the same defect resolved the opposite way -- "later id wins",
which silently priced on in-running prices.

|---|---|---|
| settled value bets | 1,133 | **1,982** |
| overall ROI | −3.54% | **−2.05%** |
| `player_win_a_set` | −6.6% (195) | **+6.7% (396)** |
| `player_total_games` | −17.2% (159) | −13.0% (351) |

**And the gate closed.** `player_aces` no longer beats the market on Brier once

`player_win_a_set` is now the most interesting family: 22.4% market coverage,
100% settleable, 7.8% takeout, and +6.7% over 396 walk-forward bets. It is not
gate-eligible yet and that ROI is one sample, not a finding.

### Phase 7: the held-out window

Split at 2026-07-30 — 1,018 training matches, 809 held out.

**The margin fix generalises.** Refitted on training data alone the slope comes
back 10.46 (shipped 11.26, old 6.15), and on the held-out window it cuts mean
margin error from 4.932 games to 4.814. Paired bootstrap over the same
fixtures: **+0.119 games, 95% CI [0.076, 0.164], P(no improvement) = 0.000.**

**The ROI does not.**

| formal profile | train | holdout |
|---|---|---|
| overall | +1.10% (1,452) | **−10.67% (530)** |
| `player_win_a_set` | +14.15% (277) | −10.51% (119) |
| `player_aces` | +20.25% (24) | −11.17% (6) |
| `player_game_handicap` | −0.39% (737) | −12.89% (279) |

The windows are not like-for-like, and the reason matters: **ITF is 8.5% of
training bets and 49.1% of holdout bets**, because ITF ratings only became
thick enough to clear the filters late in the corpus. A chronological split
here compares two different strategies, not one strategy over time.

Bootstrapping the tiers separately settles it:

| slice | n | ROI | P(ROI ≤ 0) |
|---|---|---|---|
| TOUR, train | 1,228 | +1.96% | **0.289** — never significant |
| TOUR, holdout | 227 | −17.93% | **0.988** — real |
| ITF, both windows | 383 | −5.77% | 0.888 |
| non-ITF, both windows | 1,599 | −1.16% | 0.651 |

**No window and no tier shows a credible profit.** `player_win_a_set`'s +6.7%
over the full period was a training-window streak that was never statistically
positive. The profit gate refused it at P(loss) = 17%, and the holdout says the
gate was right.

### What the out-of-sample work changed

**ITF is priced and logged but never staked.** Measured on 482 settled
fixtures: our match probability scores Brier 0.2330 against the market's 0.1838
and AUC 0.6496 against 0.7971; bootstrapped the gap is **+0.0492, 95% CI
[+0.035, +0.063], P(model not worse) = 0.000** — the tightest, most one-sided
result in the review, and consistent across both windows. This reverses the
earlier decision to open ITF, which was taken because ITF had become
*settleable*. Settleable is not beatable. Excluding it moves the replay from
−2.05% over 1,982 bets to −1.16% over 1,599, and drawdown from −95.9u to
−78.8u.

The tier decision was made on model-vs-market skill, **not** on ROI, and the
ROI effect was only observed afterwards. Removing slices until the remainder
looks profitable is how a streak gets shipped; measuring the skill deficit
first is what makes this a different thing.

**Families now carry a recent window.** `player_win_a_set` totals +10.08% over
358 bets and would have graduated to full stakes on that, but the holdout split
showed +14.3% over its first 272 and −3.2% over the next 86: a whole-record
bootstrap cannot tell *profitable* from *was profitable*. The window is the
last 30% of a family's **date span**, not its last N bets — decay happens in
time, and a count-based tail reaches further back whenever recent days are
quiet (+2.85% versus −3.2% for the same family).

Two bars, one per tier, because the whole record already clears a bootstrap and
a weaker standard on the more relevant data makes no sense:

* **VALIDATED (2u)** — recent window credibly profitable
* **EARLY_MAIN (0.5u)** — recent window merely not losing

`player_win_a_set` lands at +0.32% over its last 122 bets with P(loss) = 0.497.
Flat, not an edge. It opens at **EARLY_MAIN and 0.5u**.

**And the card still printed nothing.** The quality rule asked "is this
snapshot old?" when it needed to ask "has this match already been played?" —
the backfill branch used a two-day threshold, so every snapshot rebuilt the
morning after its match still went through the wall-clock staleness check. On
2026-08-08 all 47 priced matches scored 0, every derived family lost its value
flag, and the gate could be open while the card read 今日無清晰好注.

### M6 in detail, because it is the one that could mis-settle a live bet

The audit's 26.9% counted result **rows**, and `match_results` holds up to three
rows per match — the same trap found six other places. What decides a settlement
is the row `_BEST_SCORE_ROW_SQL` picks, so that is what was counted:

- 53 matches where *any* row says retired
- 51 where the **chosen** row says retired
- **2 where another row says retired and the chosen one does not** — those are
  the dangerous ones, since the settler grades them as ordinary completed
  matches. **0 value bets were graded on those 2.**

Every value bet on a retired match settles **VOID at 0.00u** — checked across all
50: `player_game_handicap` 20, `player_win_a_set` 2, `first_set_winner` 3, and so
on, none carrying P/L. So the handling is consistent, not inconsistent.

**One known divergence, documented rather than "fixed" blindly.** Voiding is
conservative and it will not always match Sportsbet. If an underdog wins a set
and the opponent then retires, a book that settles "to win a set" as WON pays it
while our ledger records VOID. Our ROI would understate rather than overstate,
which is the safe direction, and correcting it needs Sportsbet's actual
settlement terms — not a guess. At 2 affected bets in the whole record it changes
nothing measurable today.

### The remaining test gap that mattered: provider date handling

`providers/` is 19 files and the parse-statistics path is well covered (8 tests

11 tests added (`tests/test_provider_dates.py`), each a case the feed actually
produces:

- a 22:00 UTC fixture is **tomorrow** in Sydney — European night play, the
  largest single cohort
- the day boundary is exact at 14:00 UTC in August
- **DST is handled by the zone, not a fixed +10** — Sydney is +11 in January,
  and January is the tennis calendar's biggest month
- all seven key names the feed has used resolve; an empty one does not shadow a
  usable one, because a dropped fixture is a silent fixture
- a naive timestamp is UTC, not machine-local, so the parsed date cannot depend
  on where the code runs
- millisecond and second epochs resolve to the same instant
